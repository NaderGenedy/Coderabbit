## 1. Methodology

**The Welsh number is not an external validation, and this is now confirmed from code, not inferred.**
`run()` computes `cohort_spec = usable(d, SPEC)` separately per cohort, and the two specs differ in the
delivered output:

| cohort | `calon_final.json` → `qc.terms_used` |
|---|---|
| ukb | `age, sp50, male, htn_any, dm, smoke, cum_nonhdl, log_tghdl` |
| wales | `age, sp18, sp30, sp50, male, htn_any, cum_nonhdl, log_tghdl` |

Different term sets, and `cv(s, cohort_spec, resolve=False)` refits a `CoxPHFitter` inside each
cohort's own folds. There is no transported coefficient vector anywhere in the pipeline. Wales
`C = 0.7486` is internal cross-validation of a Wales-fitted model. CALON-F currently has **zero**
evidence of transportability, and the estimand behind the two headline C-indices is "how well does a
model refitted here do here" — twice — not "does this model travel".

**The comparator deltas and the headline C-index are two different estimators of the same model.**
`cv()` returns `c = float(np.mean(cs))` — the mean of the per-repeat C-indices — but returns `lp` as
`acc/cnt`, the *averaged* linear predictor across repeats. `delta_ci` is then called on that averaged
LP. So the model C inside every verdict is `C(mean LP)`, while the published `c_index` is
`mean(C per repeat)`. These are not equal, and the difference has a direction (lens 2).

**Estimand for the tally is not stated.** 13 subgroups = ALL plus six complementary pairs, so every
participant sits in 7 of 13 rows; 39 UKB cells from 3 comparators are heavily dependent, with no
multiplicity control in `run()` (lines 419–454). A "10 wins" count over dependent cells is not a
test statistic and should not be reported as one.

## 3. Adversarial audit

**I assumed my own r1 objections were wrong, and one of them was.** OBJ-008 claimed the exactly-zero
Wales no-diabetes Montreal delta came from `d.hdl.fillna(1.35)` → `hdl.std() == 0` → NaN vector. That
is **refuted** by the delivered file: the stored `comparator_c` for that cell is 0.7244553065363216

OBJ-023 — "the comparator LP being the model's own LP" — is refuted too: the three comparators in
that same cell return three distinct values (0.724455 / 0.727679 / 0.722427), none equal to the model's
0.722878. Both named mechanisms are dead. I have withdrawn OBJ-008 and answered OBJ-023 on that basis.
The *real* defect in that neighbourhood is Finding 1, which is larger and now filed as OBJ-028.

**I assumed grok's OBJ-025 was right and it is partly wrong.** It states "`outputs/calon_final.json`
as delivered has events and C but no n". It does: `ukb.qc.n = 3333`, `wales.qc.n = 1159`, and every
subgroup cell carries its own `n`. The main 3333-vs-3209 claim stands and duplicates OBJ-021.

**Strongest version of the panel's WIN claim, attacked.** Suppose the Julius comparator C-indices are
simply wrong and the local ones right — OBJ-001 resolves in the project's favour. The WINs still do
not survive intact, because: (a) the model C driving every delta is the ensemble-averaged LP, +0.00074
on average above the C reported as the model's discrimination, favouring the model in 21/23 subgroups;
(b) all 69 cells are within-subgroup refits, so the tally measures a *procedure*, not a frozen model;
(c) the Welsh arm is refitted, so 0/30 Welsh cells were never external anyway; (d) the model's only
published calibration belongs to a discarded specification. None of these depend on which comparator
implementation wins the PDF arbitration.

**Where I think the panel is over-reading.** codex's OBJ-017 says the centred/uncentred factorial is
non-diagnostic because additive centring moves the intercept, not the slope. That holds when `p` comes
from a logistic model. The pack's own `safeheart_risk` is `1 − S0**exp(x)` — a complementary
log-log form — and `calib_slope` regresses the event on `logit(p)`. A constant added to `x` is a
multiplicative change in `exp(x)`, which is *not* an affine shift of `logit(p)`, so the logit-scale
slope **will** move. The factorial is not vacuous. codex's own affine-invariance unit test is still the
right thing to run, and I have kept the objection on the record rather than dismissing it.
